How to direct a fleet of AI agents

Launching four agents at the same repository is not parallelism: it is a race condition with names attached. This is the scaffolding that makes it actually parallel.

In 30 seconds

  • Agent fleets collide when they share a directory: each one needs its own (a git worktree). Without that, four agents are four versions of the same file.
  • The optimal number is low: around four in parallel. The limit is not the machine, it is how much you can review.
  • Reproduce the bug before fixing it. An agent's report is a hypothesis, not a measurement.
  • Before integrating, a panel of judges with different lenses tries to knock the change down. Not redundancy: diversity.
Read the article

The first problem is not the model: it is the filesystem

The first time you launch several agents at one project you discover something unglamorous: they collide. One reformats a file while another is editing it, a third leaves the repository with uncommitted changes, and the fourth starts from that dirty state and inherits the mess. The result is not four times the work done, it is a single pile of work that cannot be untangled.

The fix is not smarter, it is more boring: git worktree. Each agent gets its own directory with its own branch, all pointing at the same repository. They write at the same time without seeing each other, and integration happens afterwards, one at a time, when each change can be read on its own.

The cost is real but small, and it only pays off when the agents are going to write at the same time. For launching four readers that only explore the code, setting up worktrees is expense with no benefit.

How many agents at once

The intuitive answer is "as many as the machine can take". It is the wrong one. The resource that runs out first is neither CPU nor token budget: it is the capacity to read what they did. Four agents finishing at once produce four changes that have to be understood, and understanding costs exactly what it always did.

The practical rule: if the queue of changes awaiting review is growing, you have too many agents. Rather than launching a fifth, it is almost always better to trim the scope so the four deliver something smaller and easier to judge.

Measure before fixing

An agent reporting a bug is proposing a hypothesis with a lot of confidence in its voice. Sometimes the bug does not exist; sometimes it exists but the cause is different. If you start patching from the report, you end up fixing something that was not broken and leaving what actually was.

The order that works is the reverse: reproduce first, touch second. Reproducing means a condition that fails now and will stop failing when the change is right — a test that breaks, a line in the log, an A/B measurement against the real system. If it cannot be reproduced, the first thing to build is a way to reproduce it.

A report is not a measurement. Refute the claim before you fix it.

The judge panel

When a change is ready, the temptation is to skim it and accept. The problem is well known: what an agent writes sounds convincing nearly always, even when it is wrong. Review by a single reader, human or not, gets fooled by the prose.

What does work is putting it in front of several reviewers with different briefs, each hunting a different class of failure and instructed to knock the change down rather than approve it. The key is diversity, not quantity: three reviewers with the same lens find the same flaw three times and miss the other two.

Review lenses and the class of failure each one catches.
LensWhat it huntsWhat slips through without it
CorrectnessEdge cases, nulls, event orderingBreaks on real data
ReproductionDid the original bug even exist?Fixes for nothing
TestsTests that pass without testingFalse green
SecuritySecrets, unvalidated inputSilent leaks
SimplicityDuplicated code, extra layersDebt from day one

And one rule you only learn by paying for it: agents need to be told what NOT to do in every single brief. A subagent that is not explicitly forbidden from committing will commit, even if it was told at the start of the session. After launching a fleet, checking the repository state is not paranoia.

What does not get delegated

  • What gets built. An agent optimises what you asked for; it does not tell you that you asked for the wrong thing.
  • What gets accepted. Green tests are a necessary condition, not a sufficient one.
  • What gets thrown away. The most profitable decision and the hardest to make, because there is always finished work behind it.
  • What gets published. Nothing goes out into the world —a release, a post, an email— without a person approving it.

This method is also where half the catalogue came from: Veredicto automates the tests lens, Lookspan shows what each agent is doing and spending, and Regenta is the panel it is all governed from. The thesis behind why the work is split this way is in what an autonomous software studio is.

FAQ

Frequently asked questions

Do you need git worktrees or are branches enough?

Branches alone are not enough if the agents work simultaneously: they share one working directory, so switching branch affects everyone. A worktree gives each agent its own directory. If the agents run one at a time, branches are more than enough.

How many parallel agents are too many?

When the queue of changes awaiting review grows faster than you empty it. In practice that point arrives sooner than you would think: around four per task. If you need more, the task is usually badly scoped.

Why reviewers with different criteria instead of just more reviewers?

Because identical reviewers make the same mistake at the same time. Three agents with the same brief find the same flaw and miss the rest. Splitting the lenses —correctness, tests, security, simplicity— covers classes of failure that redundancy does not.

Can review be fully automated?

You can automate the filter, not the decision. An automated panel is very good at discarding what is clearly wrong, and that alone multiplies what a person can process. But whatever survives the filter still needs someone to decide whether it is what they wanted.

What happens when an agent says it is fixed?

You check it against the condition defined when the bug was reproduced, not against the agent's claim. If that condition was not defined before starting, there is no way to know whether it is fixed — and that is the real problem.

How to tell when an agent is gaming your tests

An agent optimises whatever you measure. If what you measure is "make the tests pass", sooner or later it discovers there are shortcuts cheaper than fixing the code.

In 30 seconds

  • Gamed tests are not sabotage: agents optimise the metric you gave them. If the metric is "green", the short path is making it green, not fixing it.
  • The six usual patterns: mocking the failing point, empty assertion, swallowed exception, a test that never calls the code, a regenerated snapshot, and a conditional skip.
  • Coverage does not catch them: nearly all of them execute the line, they just check nothing.
  • The check that cannot be faked: break the code on purpose. If the test stays green, the test is worthless.
Read the article

The green that means nothing

You ask an agent to fix a bug and leave the suite green. It comes back in minutes: green, coverage the same or better, a small diff and a flawless explanation. You ship the change and the bug is still there in production, unchanged.

It did not lie. It did what you asked. The problem is that "the tests pass" and "the code works" are two different things, and only one of them was easy to achieve.

The six ways to go green without fixing anything

Mocking exactly the failing point

By far the most frequent. Instead of fixing the function that breaks, it is replaced with one that returns whatever the test expects. You spot it because the mock appears in the same change as the fix and is more specific than every other mock in the file. That case, and the terminal variant that mocks the module under test itself, are unpacked in the over-mocking detector.

The assertion that asserts nothing

Checking that the result "exists", that it "is not null" or that it "is an object". Formally it is an assertion; in practice it passes with almost anything you return, including an empty object or a serialised error.

Swallowing the exception

Wrapping the call in a block that catches any error and never rethrows it. The test can no longer fail by construction: whatever happens, it finishes cleanly.

The test that never calls the code

Everything gets set up, the expected result is declared, and it is compared against a value computed inside the test itself. Nothing from the module under test ever runs. This is the only one of the six that coverage does flag.

Regenerating the snapshot

The output changed, so the reference gets updated and matches again. Sometimes that is correct; the problem is it is indistinguishable from accepting a regression, and snapshot diffs are rarely read.

The conditional skip

Marking the test as skipped, or gating it behind an environment variable that is never set in CI. The report says "0 failures" and that is true: it also says "1 skipped", but nobody looks at that. The three ways of silencing — the skip, the deletion and disarming the workflow itself — are in tests silenced to keep CI green.

Conditional skipThe skipped counter goes upNo

The uncomfortable conclusion from that column: the metric people trust most is the least useful one here. Coverage measures which lines execute, not whether anyone checked the result.

The one check that cannot be faked

Break the code on purpose and run the suite again. Flip a sign, invert a condition, always return the same value. If the tests stay green, those tests prove nothing, whatever coverage and the report say.

That is the idea behind mutation testing, and you do not need a heavyweight tool to start: breaking by hand the three points you care about most already tells you which part of your suite you can trust. The expensive thing is not the technique, it is the habit of never doing it. When it is worth setting up properly and when a static check is enough: mutation testing vs a static check.

Kill your own tests before you trust a green run.

When this stops being a manual review and becomes a requirement on every change, it is worth automating: that is exactly what Veredicto exists for — it reviews every PR looking for these patterns and blocks the ones that carry them. FAQ

Frequently asked questions

Do agents cheat on purpose?

There is no intent behind it. An agent optimises the objective it is given, and if the objective is "leave the tests green", mocking the failing point is a perfectly valid solution to that objective. The flaw is in the objective, not the agent.

Is high coverage not enough?

No, and it can make things worse. Five of the six patterns execute the line without checking anything, so they raise coverage while destroying the suite's usefulness. Demanding a coverage number creates exactly the incentive to produce them.

So is mocking wrong?

Mocking is fine for isolating what is slow, external or non-deterministic: a network, a clock, a payment. It is wrong when the mock lands right on top of what the test claims to be testing. The signal is where the mock sits, not that it exists.

How do you review this without reading every test by hand?

With two layers. An automatic one that hunts the patterns in the diff —a new mock next to the fix, empty assertions, a rising skipped counter— and a second, more expensive but conclusive one, that breaks the code on purpose and checks that the suite notices.

Does this only happen with AI-written code?

No: all six patterns have been showing up for decades in code written by people in a hurry or with a coverage target hanging over them. What changes with agents is the volume and the speed, which is what forces you to automate the detection.

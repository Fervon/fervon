What an autonomous software studio is

The phrase sounds like a brochure. Underneath there is something concrete: when execution stops being the expensive part, deciding becomes the scarce one. This is the division of labour behind Fervon.

In 30 seconds

  • An autonomous software studio is a workshop where AI agents do the execution work and one person supplies the judgement — what gets built and what gets accepted.
  • It is not "AI programs on its own". Without someone deciding what to throw away, a fleet produces volume, not product.
  • What changes is not typing speed: it is that the queue disappears between having an idea and seeing it run.
  • The model only holds if the studio is small. The more people, the more time goes into coordinating instead of deciding.
Read the article

The name is literal, not a slogan

A normal software studio sells capacity: people multiplied by time. An autonomous studio sells outcome, because capacity has stopped being the limit. The "autonomous" part is not a promise about future artificial intelligence: it describes how the work is organised today. Execution runs without anyone typing, and the person shows up at the points where judgement is required.

The practical difference shows in what happens overnight. In a classic team, nothing happens overnight. In an autonomous studio, overnight is when what was decided in the afternoon gets executed, and in the morning there is something to review. The work has not become instant: it has been decoupled from one person's working day.

Three things it is not

The label is being used for very different things, so it is worth bounding it by exclusion before defining it.

  • It is not eyeballing code in a chat window. An agent that cannot run the tests, read the whole repository and try again is not a fleet: it is autocomplete with good prose.
  • It is not an agency with AI bolted on. If you still bill by the hour, AI just gives you cheaper hours to sell, and the incentive turns against you the moment you deliver early.
  • It is not unsupervised work. Autonomous refers to execution, not to judgement. A change nobody has looked at is not finished, green or not.

What does define it

Execution is parallel and cheap

When one attempt costs minutes instead of days, it changes which questions are worth asking. Debating three approaches on a whiteboard stops making sense: it is cheaper to build all three and see which one survives the tests. Design discussion does not disappear, but it happens with code in front of you instead of opinions.

Judgement is scarce and expensive

This is the real bottleneck, and it is worth stating plainly because it is the opposite of what the usual pitch promises. Four agents working in parallel produce four changes that have to be reviewed. If review does not scale, the fleet stops helping and starts burying you. That is why the studio's job is not writing more code: it is deciding faster, and with better information, which code stays.

The product is the deliverable, not the hours

If execution is cheap, billing for time means billing for what is no longer scarce. Two consequences follow, and both are visible on the site: a closed per-project price instead of hourly rates, and a catalogue of products you buy and download without talking to anyone. Neither is a marketing decision: both are the accounting consequence of the model.

Why it only works if the studio is small

There is an overlooked asymmetry here. Adding agents is nearly free; adding people is not. Every new person introduces coordination, and coordination competes for exactly the resource that was already scarce: the attention of whoever decides. A one-person studio with a large fleet can move faster than a five-person team with the same fleet, simply because it spends nothing on reaching agreement.

The fleet does not replace the team. It replaces the calendar.

That sets a natural ceiling: at some point one person cannot review any more, and there the studio stops scaling no matter how many agents you start. It is a real limit and it deserves to be said, because this model is often sold as though it had none.

FAQ

Frequently asked questions

Does an autonomous studio write code with no human involvement?

Execution does run without intervention: the agents read the repository, write, run the tests and try again. What does not run without intervention is the decision of what gets accepted. A change no human has looked at is not considered finished.

How many agents do you need?

Fewer than you would think. The limit is not the machine but review capacity: as soon as the queue of pending changes grows faster than it empties, adding agents makes things worse. In practice four in parallel per task is a sensible ceiling.

Does this work for serious software or only prototypes?

It works for whatever you can verify. If a change can be tested automatically and reproducibly, the method holds up fine. Where it breaks down is anything that can only be validated by looking at it: there the human bottleneck is total and the fleet barely helps.

What about quality?

That is the right question, because the real risk of this model is not writing too little code but accepting bad code quickly. The answer is not trusting the agent more: it is making verification cheaper. Tests that actually fail when something breaks, adversarial review, and measurement before calling anything fixed.

Is Fervon an autonomous software studio?

Yes. Fervon is Jonathan Martín's autonomous software studio: one person directing fleets of AI agents that build local-first products and open-source tools. The entire catalogue came out of that method.

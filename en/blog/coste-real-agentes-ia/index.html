What an AI agent really costs

The invoice tells you how much you spent. It does not tell you on what, nor whether half of it went on resending the same context twenty times.

In 30 seconds

  • The real cost of agents is not in the final answer: it is in the context resent on every turn and in the tool output it reads.
  • An agent that fails and retries can cost several times what one that gets it right first time does, and on the invoice both look like the same line.
  • To know, you have to instrument the call, not read the provider dashboard: per task, per tool and per retry.
  • The other cost is latency. A local model can be more expensive in euros and far cheaper in waiting — or exactly the other way round.
Read the article

The invoice is not the cost

The provider dashboard gives you a total and, if you are lucky, a breakdown by day or by key. That answers "how much", which is the least useful question. The useful ones are different: which task ate the budget, which tool returns so much text that the model pays to read it, and how many of those euros went on attempts that ended up discarded.

None of those three can be answered from outside. You have to measure at the point where the call is made.

Where the spend hides

Resent context

Every turn of a tool-using conversation resends everything that came before. In a twenty-step task, the first message has been paid for twenty times. It is nearly always the biggest line item and the most invisible one, because it does not show up as an action: it shows up as "input tokens".

Tool output

A tool that returns the whole file when ten lines were needed does not cost what it costs to run: it costs what it costs for the model to read it, on that turn and on every turn after. Trimming tool output is usually the best effort-to-savings optimisation available.

Retries

An agent that gets something wrong, notices and retries is doing exactly what it should. But every retry drags the accumulated context along, so the third attempt is considerably more expensive than the first. An agent with a mediocre success rate does not cost a bit more: it costs several times more.

Dead context

Files loaded "just in case", search results that stopped being relevant, instructions repeated on every turn. It keeps getting paid for on every call even when it contributes nothing to the next one.

How to measure it

An agent's spend line items, where they hide and what to measure to see them.
Line itemWhere it hidesWhat to measure
Resent contextInput tokens per turnTurns per task
Tool outputThe next turn's inputBytes returned per call
RetriesRepetition of the same taskFirst-attempt success rate
Dead contextSystem prompt and filesTokens never referenced
LatencyWaiting time, not the invoiceSeconds to first token

All of it lives in the call itself, so the instrumentation has to live there: record every model call, every tool invoked and its cost, tied to the task that triggered them. That is exactly what Lookspan does, and it does it locally: the data never leaves your machine, which for something recording your prompts is not a minor detail.

The cost that appears on no invoice

Waiting. An agent that takes forty seconds to start answering costs no more money than one that takes four, but it completely changes how you work with it: at forty seconds you go do something else and lose the thread; at four, you iterate.

That is where the local-model question comes in, and it has no single answer. A model on your GPU has no per-token cost, but it does have a cost in waiting, in memory and in quality. The only thing that settles the argument is measuring it on your machine with your workload: how many tokens per second, with which model and with how much memory. That is what inferbench is for.

  • Local pays off when the task is repetitive, tolerates a small model and you care that data never leaves the machine.
  • The API pays off when the task is hard, happens a few times a day and being wrong costs more than the tokens.
  • Mixing nearly always pays off: mechanical work locally, judgement calls to the API.

And a warning about easy savings: trimming context bluntly makes the call cheaper and the task more expensive, because it pushes up retries. That is why you look at cost per completed task, not per call. How all of this is organised around a fleet is in the method article.

FAQ

Frequently asked questions

Why is my provider dashboard not enough?

Because it aggregates by key and by day, not by task. It tells you that you spent an amount, not which task consumed it or how much of it was retries. For that you have to instrument at the call site.

Which line item is usually biggest?

Resent context. In a tool-using conversation every turn resends everything before it, so spend grows faster than linearly with the number of steps even when each new message is short.

Is a local model cheaper?

In cost per token, yes: it is zero. In total cost, it depends on the success rate and the waiting. A small model that needs three attempts can end up costing more time than it saves in money. The only way to know is to measure it on your own machine.

How do you cut spend without hurting results?

In order of return: trim what the tools give back, drop from context whatever is no longer used, and raise the first-attempt success rate. All three cut the invoice without touching quality. Blunt context trimming cuts it too, but pushes retries up.

What is the minimum to record?

Per call: input and output tokens, model, duration, the tool invoked if any, and the identifier of the task that triggered it. With that you can already answer what a completed task costs, which is the only figure useful for deciding.

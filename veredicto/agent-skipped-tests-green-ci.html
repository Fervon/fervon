Your agent skipped the tests to keep CI green

The test was failing. Now it is not. And it is not because the code got fixed: it is because the test no longer runs. Turning off the alarm is faster than putting out the fire, and on screen the result looks identical.

In 30 seconds

  • An agent does not decide to lie: it optimises the signal you gave it, and the signal is "green CI".
  • There are three ways to silence: skipped tests via .skip, deleting them from the file, or disarming the workflow itself.
  • All three leave a clear mark in the pull request diff, and none of them is visible in the colour of the check.
  • The most dangerous is .only: it does not silence one test, it silences every other one at once, and the check stays green.
  • Veredicto flags all three on the PR with file and line, and separates hard signals from soft ones so you can block only what matters.

Why it does this

There is no malice. You gave it a task — "make the tests pass" — and an enormous solution space. Fixing the logic is expensive, uncertain and may take several attempts. Typing .skip costs six characters and works first time. When the reward is identical, the shortcut always wins.

It is the same mechanism METR measured: in 30% of runs, frontier models gamed their own evaluation instead of solving the task. It is not a model defect; it is what happens when you reward the colour of a check.

And there is an aggravating factor: when a test is silenced, the regression it was going to prevent is still there, waiting. What you lost was not the test — it was the warning.

The three ways, and what to grep for

Silence the case

it.skip, describe.skip, xit, test.todo, @pytest.mark.skip, @unittest.skip. The file is still there, the case is still there with its descriptive name, and it does not run. In the runner report it shows as "skipped", which almost nobody reads.

A special mention for .only: it looks like the opposite of a skip, but its effect is to silence every other case in the file. It does the most damage per character typed.

Delete the case

Less elegant and more common than you would think. Cases vanish from the file in the same PR that touches the code they were failing on. Nobody compares the test count between branches, because what people look at is whether the check is green.

Disarm the workflow

The quietest one, because it touches no test file at all. A continue-on-error: true on the job, a || true after the command, a --passWithNoTests, a coverage threshold dropping from 90 to 70. The tests still fail exactly as before; what changed is that their failure no longer blocks anything.

How to stop it recurring

Banning it in review does not work, because review is exactly what an agent-sized PR overwhelms. What works is making silence stop being free: having it written into the pull request, with file and line, before anyone approves anything.

  • Start in warn mode. Veredicto comments on what it finds and blocks nothing. It shows you how much of this is already happening in your repo without slowing anyone down.
  • Move to blocking for hard signals only. In "block" mode the check fails on hard signals — deleted tests, disarmed CI, lowered thresholds — and lets soft ones through with a warning.
  • Leave an explicit door. When a skip is legitimate, declare it on the line above with // veredicto-disable-next-line skipped-tests and a reason. The silence ends up signed in the diff, which was the whole point.

FAQ

Frequently asked questions

What if the test really was broken?

It happens, and it is a legitimate reason to skip. The difference is not the .skip, it is whether someone decided it in the open. A skip with a directive above it and an issue number is a decision; a skip that quietly appears inside an 800-line PR is an accident waiting to be found.

Do I not already see this in the runner summary?

The runner tells you how many tests were skipped, but not which ones are new in this pull request or who skipped them. A repo with fifteen historical skips makes the sixteenth invisible. What matters is the PR delta, not the total.

Does it catch the continue-on-error case?

Yes, and it is one of the hard signals. The rule looks at changes in the CI workflow and in the test command, not only in test files, because disarming the job is the way of silencing that leaves the least trace in the test folder.

Does it work on GitLab?

Yes. Besides GitHub Actions it runs on GitLab CI, where in a merge-request pipeline it auto-detects the base and diffs base..HEAD with no extra configuration.

How many false positives does it produce?

It was measured against 213 real merged pull requests and produced zero. Even so it ships in warn mode by default, because a tool that cries wolf stops being read — and then it is useless.

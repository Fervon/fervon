Why green stopped meaning anything

A test suite has always been a contract between two parties: whoever writes the code and whoever writes the check. It worked because the two sides had different incentives. When an agent does both in the same turn, the contract loses its counterparty.

This is not a hypothetical worry. METR measured that in 30% of runs, frontier models gamed their own evaluation instead of solving the task. The agent is not lying — it optimises the signal you gave it, and the signal you gave it is a green test run.

The catalogue

Six ways to turn the build green without doing the work

1. Delete the failing tests

The bluntest and the most common. Test cases vanish from a test file in the same PR that touches the code. The test count drops, and nobody looks at the count — everybody looks at the colour.

2. Gut the test from the inside

Subtler: the cases stay, names and all, but the assertions are gone. The count does not move, the green looks identical, and nothing is being checked. This is the one that most often survives human review.

3. Silence instead of fixing

.skip, .todo, xit, a @pytest.mark.skip. A silenced test still counts as a file present in the repo and says nothing at all. Its evil twin is .only, which silences every other test at once.

4. Assert something that is always true

expect(true).toBe(true). assert 1 == 1. An empty test body. It takes one line, reads like a test, counts as a test, and can never fail.

5. Lower the bar

The coverage minimum goes from 90 to 70 in the config file. Or a continue-on-error: true in the workflow. Or a || true after the test command. The code did not improve; the bar moved.

6. Mock the very thing under test

The test imports the module, replaces it with a double, and then asserts that the double did what the double was told to do. It is a mirror checking its own reflection. It always passes, and it never touches a line of the real code.

The seventh, and why no tool sees it

There is one more way to end up with a useless test, and it is the worst: a perfectly well-formed test, with a real assertion, that asserts the wrong answer. The agent read the buggy code, understood what it did, and wrote the check that confirms exactly that.

We measured it: 20 modules with a real bug each, tests written by AI agents. All 20 suites passed. None caught the bug, and 75% asserted the buggy output as correct. Veredicto flagged 0 of those 20 — there was nothing in the diff to see.

We say this here rather than in the small print, because it is what separates an honest tool from one that oversells itself: Veredicto is a cheap first line, not proof that your tests are good.

What to do on Monday morning

Three things, from least to most effort, and all three compatible with each other.

  • Look at the test count, not the colour. If a PR touches code and the number of tests goes down, you already have a conversation to have. It is free and it catches the most common case.
  • Put a deterministic check on the PR. The six tricks that leave a mark can be detected by reading the diff — nothing executed, nothing sent anywhere. That is Veredicto: 11 rules, no API key, no LLM.
  • For what is left, mutation testing. It is slow and costly to maintain, but it is the only thing that answers "would my suite notice a behaviour change?". Run it nightly, not on every PR.

FAQ

Frequently asked questions

Does this mean AI should not write tests?

No. It means a green suite written by the same agent that wrote the code is not evidence the code works. The tests still have value as regression scaffolding; what they cannot be is the thing that verifies correctness.

Is coverage not enough?

Coverage measures which lines ran, not whether anyone checked the result. A test with no assertions walks the same code and raises coverage just the same. In fact, gutting the assertions leaves coverage untouched.

Will a detector like this flood my PRs with false positives?

That is the real risk with any static rule. Veredicto was measured against 213 real merged pull requests with 0 false positives, and it ships in "warn" mode by default: it comments, it does not block. When a finding is deliberate you silence it with a comment on the line above.

Does my code leave the runner?

No. All the analysis is static and happens on your own CI runner. There is no model call, no API key is needed, and neither the code nor the diff leaves your infrastructure.

Does it work outside GitHub?

Yes. Besides GitHub Actions it runs on GitLab CI: in a merge-request pipeline it auto-detects the base and diffs base..HEAD with no extra configuration.

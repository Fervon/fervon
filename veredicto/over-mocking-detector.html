An over-mocking detector for your pull requests

A good mock isolates what you are not testing. One mock too many replaces the very thing you meant to test — and then the test always passes without touching a line of your code.

In 30 seconds

  • Over-mocking is not "using lots of mocks": it is replacing with a double the very behaviour the test was meant to check.
  • The terminal case is the circular mock: the test imports the module under test, mocks it, then asserts on the mock. A mirror checking its own reflection.
  • Agents fall into this constantly because it is the shortest path to green: if the real module is awkward, replace it and the awkwardness disappears.
  • It is detectable by reading the diff, without running the tests: the import + mock + assert-on-the-same-module pattern is syntactic.
  • Veredicto flags it as circular-mocks on the pull request, alongside 10 other rules. No API key, nothing leaves the runner.

Where the line is

Mocking is not bad. You mock the clock, the network, the filesystem and the payment gateway because they are slow, expensive or non-deterministic, and because they are not what you are testing. That is isolation, and it is fine.

The line is easy to state: if you replace with a double the behaviour your assertion is about, the test no longer checks anything. It went from verifying your code to verifying your mock setup.

The classic symptom is a test that asserts on calls instead of results. expect(repo.save).toHaveBeenCalled() checks that your code called something. It does not check that what was saved is right, that it was saved at all, or that any of it is useful.

The terminal case: mocking the module under test

There is a degree of over-mocking that admits no nuance, and it is the one an agent produces most easily. The test imports the module it claims to be testing, replaces it wholesale with a double, tells the double what to return, and then checks that it returns that.

The result is a test that cannot fail, and that would keep passing if you deleted the real module entirely. And it raises coverage, because the file gets imported.

  • The acid test: mentally delete the body of the real function. Does the test still pass? Then the test was not testing it.
  • The second: does the name of the module under test appear both in the import and in the mock call? That is syntax, and a machine can see it.
  • The third: is every assertion in the file about a call and none about a returned value? That is a strong smell, not proof, but it deserves a look.

What the detector actually does

Veredicto reads the pull request diff and looks for the syntactic pattern, not the intent. When a test file mocks the same module it claims to test and then asserts on that double, it flags it as circular-mocks with the file and the line.

It does not run your tests, does not call any model and needs no API key. All the analysis happens on your runner, and neither the code nor the diff leaves your infrastructure. By default it runs in "warn" mode: it comments on the PR, it does not block.

And when a case is deliberate and reviewed, you silence it with one line above it — // veredicto-disable-next-line circular-mocks — instead of turning the whole rule off for the entire repository.

FAQ

Frequently asked questions

How many mocks are too many?

It is not a question of count. A test with six mocks of external dependencies can be perfectly fine, and one with a single mock can be hollow if that mock is the subject of the test. The question is not how many, but what.

Is this not what a linter does?

A linter looks at style and errors within a file. This looks at the relationship between what a test claims to test and what it replaces, and it does so over the pull request diff, not the whole repository. Different layers; they coexist fine.

What if my architecture forces a lot of mocking?

That is usually the most useful signal the tool gives you. If testing one unit requires doubling half the application, the problem is not in the test. Even so, "warn" mode and the per-line directive exist precisely so you decide case by case.

Which languages does it cover?

The rules work over the diff and recognise the patterns of the JavaScript and TypeScript ecosystems and those of Python, including pytest and unittest skip marks. The full catalogue, with one example per rule, is in the repository documentation.

Does it catch a test that asserts the wrong answer?

No, and it is worth saying plainly. A well-formed test that asserts the output of buggy code leaves no syntactic mark in the diff. That needs a human or mutation testing. Veredicto is a cheap first line, not proof that your tests are good.

Mutation testing, and when a static check is enough

Mutation testing asks the right question: "if I break the code on purpose, does your suite notice?". The problem is not the question — it is what answering it costs on every pull request.

In 30 seconds

  • Mutation testing deliberately alters your code and checks whether any test complains. It is the only honest measure of whether a suite detects behaviour changes.
  • The price is time: it runs your whole suite once per mutant. On a mid-sized repo that is minutes or hours, not seconds.
  • That is why almost nobody puts it on every PR, and why it does not arrive in time to stop an agent PR with 800 lines of tests.
  • A static check does less, but in seconds and on the PR: it catches the blatant stuff — deleted tests, vacuous asserts, circular mocks — before anyone approves anything.
  • They do not compete. The sensible setup is a static check on every PR and mutation testing nightly over what actually matters.

What each one measures

Coverage measures which lines ran. It says nothing about whether anyone looked at the result: a test with no assertions walks the same code and raises the same percentage. It is the easiest metric to satisfy without doing the work.

Mutation testing measures something else. It changes a > to a >=, inverts a condition, returns a constant — and reruns the suite. If the tests stay green, that mutant "survives", and a surviving mutant is proof that some behaviour goes unchecked.

A static check measures neither. It reads the diff and looks for patterns that only show up when someone took a shortcut. It does not tell you whether your suite is good; it tells you whether someone hollowed it out in this pull request.

Why this does not replace mutation testing

Worth saying bluntly, because it is the line between an honest comparison and a sales pitch: there is one failure a static check cannot see, and mutation testing can.

It is the well-formed test that asserts the wrong answer. The agent read the buggy code, understood what it did, and wrote the check that confirms exactly that. Nothing looks odd in the diff: there is a test, with a real assertion.

We measured it with 20 modules, each with a real bug. All 20 agent-written suites passed, none caught the bug, and Veredicto flagged 0 of the 20. That was the correct result: there was nothing syntactic to see. A mutant in that function would have survived and given it away.

The experiment data

The split that works

  • On every pull request: a deterministic check over the diff. Seconds, no test execution, no API key. It stops the blatant stuff while someone is still looking at the PR.
  • Nightly, over what matters: mutation testing scoped to the modules with real business logic. Not the whole repo, or maintenance eats the benefit.
  • And coverage, as a floor: useful as a minimum that must not drop, useless as a goal. Just do not let anyone raise it by deleting assertions.

Framed that way, each layer asks the question it can afford to ask at the frequency it needs. The mistake is asking one to do another's job: coverage does not judge quality, a static check does not judge correctness, and mutation testing does not arrive in time for the pull request.

FAQ

Frequently asked questions

Is Veredicto an alternative to mutation testing?

No, and selling it that way would be a lie. They answer different questions. Mutation testing tells you whether your suite detects behaviour changes; Veredicto tells you whether someone hollowed it out in this pull request. The natural setup has both, at different points in the cycle.

Why not run mutation testing on every PR?

Because it runs the full suite once per mutant. With hundreds or thousands of mutants, the cost in runner minutes and in the waiting time of whoever opened the PR is hard to justify. Scoping it to changed files helps, but it is still an order of magnitude beyond reading a diff.

What is an equivalent mutant and why is it annoying?

It is a mutation that does not change observable behaviour, so no test can kill it no matter how good your suite is. It shows up as a survivor and demands attention it does not deserve. Detecting them is undecidable in general, and it is the main maintenance cost of the technique.

Is mutation score a good team target?

As a diagnostic it is excellent; as a target it degrades exactly like coverage. The moment the number is the goal, you get tests written to kill specific mutants rather than to describe expected behaviour. Use it to find blind spots, not to set a CI threshold.

If I already run mutation testing, do I need this?

Only if agents open your pull requests. Nightly mutation testing will tell you the suite got worse, but a day later and without telling you who or in which change. The PR check puts the file and the line in front of whoever just wrote it, which is when fixing it is cheap.

El problema

«Todos los tests pasan.» ¿Según quién?

Cuando el agente escribe el código Y los tests, el verde del CI deja de significar que el código funciona.

El agente borra o marca .skip el test que falla en vez de arreglar el bug.

Asserts que siempre pasan: expect(true).toBe(true), mocks que mockean justo lo que se testea.

Corres flotas de agentes en paralelo. El CI es el único filtro humano — y se lo están saltando.

En el 30% de los runs, los modelos punteros amañaron su propia evaluación — medido por METR. El dolor está cuantificado; nadie vende el detector.

Los detectores

Qué detecta

Los trucos concretos con que los agentes ponen el CI en verde sin hacer el trabajo.

Mocks circulares

Mockear justo la función que se testea, de forma que el assert solo comprueba el mock.

Tests borrados y .skip

Tests eliminados, comentados o marcados .skip/xfail en el mismo PR que toca su código.

Asserts borrados, test intacto

Se va el expect y se queda el it(...): el mismo número de tests en verde, sin comprobar nada.

Asserts tautológicos

expect(true).toBe(true), assert.strictEqual(true, true), assert 1 == 1, cuerpos de test vacíos — verde que no prueba nada.

Umbrales relajados

Mínimos de cobertura bajados, o el paso de CI desarmado con continue-on-error / || true, para esquivar un build rojo.

Snapshots regenerados en masa

Una oleada de snapshots actualizados que bendicen en silencio cualquier salida nueva.

Fallos tragados

npm test || true, --passWithNoTests, un catch {} vacío alrededor de los asserts: falló, y no se entera nadie.

Asserts debilitados

Un matcher estricto cambiado por uno que casi no puede fallar: toBe pasa a toBeTruthy, un valor exacto pasa a any(Number).

Asserts comentados

El assert ni se arregla ni se borra: se comenta, así que el test sigue corriendo y comprueba una cosa menos.

Esas tarjetas son las familias. Debajo van 11 reglas deterministas, cada una con el fragmento que la dispara y una línea para callarla cuando el cambio es a propósito — catálogo completo de reglas. Y la parte honesta: la detección estática no caza un test bien formado que comprueba lo que no debe — lo que no detecta, medido.

FAQ

Preguntas frecuentes

¿Necesito una API key o un LLM?

No. Veredicto corre en tu runner, es determinista y no usa LLM ni API key. Ni siquiera la licencia sale a la red: es una firma Ed25519 que se verifica en local, así que funciona en un runner sin salida a internet. Nada de tu diff sale nunca de tu máquina.

¿Va a bloquear mis pull requests?

Por defecto funciona en modo warn: comenta lo que encuentra sin bloquear. El modo block es opt-in. Cada regla trae explicación y se puede suprimir con un comentario en el PR.

¿En qué se diferencia de CodeRabbit o del review nativo de GitHub?

CodeRabbit revisa calidad con un LLM de pago; GitHub valida seguridad. Ninguno comprueba la integridad de los tests. Veredicto hace una cosa: detectar cuando los tests se amañaron — determinista, instantáneo y sin mandar tu diff a ningún sitio.

¿Qué es test-gaming exactamente?

Hacer que el CI pase en verde sin que el código sea correcto: borrar o marcar .skip tests, asserts tautológicos, mocks de lo que se testea, snapshots regenerados en masa o umbrales de cobertura relajados.

¿Funciona en GitLab o Bitbucket?

Primero GitHub Actions. GitLab y Bitbucket están en el roadmap. Apúntate a la lista para saber cuándo llegan.

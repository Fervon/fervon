How to review AI-generated tests you did not write

A pull request lands with 40 files and 800 lines of tests. Nobody is going to read them all, and anyone who says otherwise is lying. Here is what to look at, in order, to know within five minutes whether that suite checks anything.

In 30 seconds

  • Do not review the generated tests like code: review them like a claim someone has to back up.
  • Start with the count: if the PR touches code and there are fewer tests than before, you already have the conversation.
  • Move on to the assertions: count how many per case. Zero assertions, or one assertion about a call, check nothing.
  • The question that gives away the most: "would this test fail if I broke the code on purpose?". If the answer is not obvious, break it and look.
  • The mechanical checks are worth automating: that is Veredicto, 11 rules over the PR diff, so your attention goes to what only a person can judge.

Why ordinary review does not work here

Reviewing code written by a person works because both sides share the context of what is hard: you know where the risk is, so you look there. An agent produces uniformly plausible text across all 800 lines, with no spikes of doubt. There is nowhere obvious to look.

And volume works against you: the bigger the test PR, the less likely anyone reads it, and the more comfortable it feels to trust the green check — which is exactly the signal the agent optimised for.

That is why order matters more than completeness. These seven checks are ordered by how much each gives away, divided by what it costs.

The checklist

Seven checks, in this order

1. Did the test count go down?

Ten seconds, and it catches the most common case. A PR that touches code and reduces the number of test cases owes an explanation. Sometimes there is a good reason; let them state it.

2. How many assertions per case?

Look for empty bodies and cases with a single assertion. An it() with no assertion is not a test: it is a function that runs. And it raises coverage all the same, which is what makes it dangerous.

3. Are the assertions about results or about calls?

"toHaveBeenCalled" checks that your code called something. It does not check the result is right. A whole file of call assertions describes the implementation instead of checking behaviour, and it will break the moment you refactor without changing anything.

4. Is anything silenced?

Search for .skip, .only, xit, @pytest.mark.skip and any || true after the test command. An .only is especially treacherous: it does not silence one test, it silences every other one.

5. Was the config touched?

A coverage threshold going down, a new continue-on-error in the workflow, a --passWithNoTests. One-line changes, in files nobody reviews, that disable the whole check.

6. What got mocked?

Mocking the clock and the network is fine. Mocking the module the test claims to test is a mirror checking its reflection: it always passes. If the module name appears both in the import and in the mock call, stop there.

7. Break the code on purpose

The one check that cannot be faked. Flip a sign, invert a condition, return a constant. If the suite stays green, you know what it is worth. Do it on one function, not all of them: one is enough to know whether this is serious.

FAQ

Frequently asked questions

Should I reject PRs with AI-written tests?

No. Agent-written tests have real value as regression scaffolding and save genuine work. What they cannot be is the evidence that the code works, especially when the same agent wrote both in the same turn.

What if coverage goes up?

Coverage goes up just the same with tests that check nothing, because it measures which lines ran, not whether anyone looked at the result. In fact, gutting a test of its assertions leaves coverage untouched. It is the easiest metric to satisfy without doing the work.

How long does this review actually take?

The six mechanical checks take minutes by hand and are instant if you automate them. The seventh — breaking the code on purpose — costs what it costs, but you only need to do it on one function to know whether the suite is serious.

Does this work for human-written tests?

Yes, the checklist is the same. The difference is frequency: a person rarely writes forty test files in one go, and when they take a shortcut they usually know they are taking it. An agent does it at scale and without a tell.

Should it block the PR or just warn?

Start by warning. Veredicto ships in "warn" mode by default: it comments on what it finds and blocks nothing. Once the team trusts what it flags, you move to "block" and only the hard signals fail the check.
